# ドッグフーディング記録(2026-10-20)

v3.0.0 のリリース版 `.app` を、本番オペレーターが使う順番で一通り操作した記録。入力はダイアログへの手入力(1 文字ずつの input イベント)とボタンのクリックで行い、結果は画面(スクリーンショット)・Host の状態・OSC 受信側(`tools/tcb3/osc_listen.py` をポート 9100 で起動)の 3 点で確認した。v2 は同じ操作ができないため、起動確認とテストの範囲に留めた(末尾)。

## 使った環境

- v3: `TimecodeBridge3.app`(v3.0.0 リリース成果物)をポート 47301・専用データディレクトリで起動。LTC は自己テスト信号(Pro Tools Audio Bridge 2-A)。
- OSC 送信先: 「QLab 本番」127.0.0.1:9100(受信側あり)と「照明卓」192.0.2.1:53000(到達不可)。
- v2: `feature/macos-app`(c855d81)を `dotnet build -o` した成果物。`HOME` を隔離して起動。

## 見つけた不具合(修正済み)

### 送信ログを開くと最古の行までスクロールしていた

ログは「新しい順」で描画しているのに、更新のたびに末尾へ自動スクロールしていた。本番走行のあとに送信ログタブを開くと 10 分前の疎通確認が先頭に見え、直前の送信が画面の上に隠れていた。先頭(最新)に追従するよう直し、ユーザーが下へスクロールして古い行を読んでいる間は位置を動かさないようにした(ブラウザのスクロールアンカーで同じ行が見え続ける)。修正コミット: `0cd12d6`。

## 使っていて引っかかった点(未修正・提案)

どれも動作は正しいが、本番オペレーターの立場では一手間増える、または誤解しやすい点。

1. **疎通確認を 2 件続けて押すと、トーストがどのホストの結果か分からない。** 「疎通 OK」の直後に「疎通できません」へ入れ替わるだけで名前が無い(送信ログには名前つきで残る)。トーストにホスト名を入れると迷わない。
2. **複製・連続複製したキューの名前が元と完全に同じになる。** 「照明 シーン 2」が 3 行並ぶと見分けがつかない。v2 と同じ仕様だが、「(2)」などの連番が付くと実務で助かる。
3. **フッターの「発火後オートミュート ON」は全体スイッチで、キュー側の「発火時ミュート」(既定 OFF)が無いと何も起きない。** v2 と同じ仕様で、ツールチップにも説明はあるが、表記だけを見ると全キューが自動でミュートされるように読める。
4. **MUTE 中に見送ったキューが送信ログに一切残らない。** 本番後に「なぜあのキューが出なかったか」を追えない。「MUTE 中のため見送り」の 1 行があると安心できる。
5. **NEXT CUE の残り時間が遠いキューでもフレーム数のまま。** 10:00:12:00 のキューを 01:15 に見ると「T− 945313f」と出る。一定以上離れたら時:分:秒で出す方が読みやすい。
6. **内部生成中もモニターの見出しが「受信タイムコード / OFFSET適用後」のまま。** 「生成タイムコード」のように状況に合わせた方が迷わない。
7. **ポン出しボタンの作成ダイアログの入力欄に aria-label が無い。** キュー編集ダイアログは付いているので揃えたい(読み上げ・自動化の両方で効く)。

## 確認して問題なかった操作

- **ホスト管理**: 名前だけで追加すると IP とポートの必須エラーが欄の下に出る。疎通確認は到達可で「0 ms」、到達不可で約 3.5 秒後に「疎通できません」。
- **キュー編集**: ダイアログ手入力で 4 件追加(型付き引数 `int32:1` / `float32:0.5` / `string:intro` も正しく保存)。追加直後は新規キューが選択状態。30 fps で FF に 35 と打つと 29 に丸まり「FF 00–29」の案内が出る。ダブルクリックで編集ダイアログが開き名前を変更できる。連続複製はタイムコード欄で間隔を指定でき、プレビュー文(「照明 シーン 2」の 01:05:20:00 から間隔ずつ後ろに並べます)が分かりやすい。時間順の並べ替え、削除確認、元に戻す(復元キューが選択状態になる)とやり直しが動く。
- **プロジェクト**: 保存 → 新規 → プロジェクトメニューの「最近使ったプロジェクト」から再オープンで、キュー 11 件・ホスト 2 件・ポン出しボタン 1 件が戻る。保存後はヘッダーが「保存済み」になる。
- **本番走行(LTC 受信)**: キューが時刻どおり発火し、受信側に `/show/go [1]` が届く。「発火時ミュート」+「ミュート解除 5 秒」のキューは発火と同時に MUTE ボタンが「自動解除まで 0:04」、行に「MUTE 0:04」のタグ、TC 入出力に「送出 MUTE」と出て、5 秒後に LIVE へ戻る。L キーで手動 MUTE 中のキューは発火せず、解除後も過ぎたキューは発火しない。
- **CUE SYNC**: 送信先 0 件で Space / 単発送信を押すと「Cue-Sync の送信先ホストを選んでください」。QLab にチェック後、Space で `/cuesync [4252.33]`(秒数 float)が届く。
- **ポン出し**: P でパネルが開き、編集モードの空セル「＋」から作成ダイアログ(ラベル / OSC アドレス / 引数 / 送信先)。ラベル未入力で保存すると「ラベルは必須です」。実行モードで押すと `/light/house/on [1]` が届き、セルに「送信しました」と出る。Esc で閉じる。
- **内部生成**: 開始 TC 10:00:00:00 を入力して ▶ 再生で走り出し、10:00:12:00 のキューが発火して OSC が届く。■ 停止 → リセットで 10:00:00:00 に戻り、LTC 受信に戻すと自己テスト信号を再びロックする(誤り率 0%)。出力デバイス「なし」が既定なのでテスト中にスピーカーから音は出ない。

## v2 について

同じシナリオを自動で流す口が v2 には無く、この端末の `screencapture` と System Events にも権限が無いため、画面を撮ることも操作することもできなかった。できたのは次の範囲。

- `feature/macos-app`(c855d81)のビルドが通り、App テスト 255 件が全件成功。
- `HOME` を隔離して `dotnet TimecodeBridge.App.dll` で起動すると 1600×868 のウィンドウが開き、1 分強そのまま安定、標準出力にエラーなし、SIGTERM で正常終了。
- 注意点: `dotnet build -o` で別ディレクトリに出した apphost(`TimecodeBridge.App` 実行ファイル)は macOS で起動直後に SIGKILL される(署名不一致)。`dotnet TimecodeBridge.App.dll` で起動すれば動く。製品の不具合ではなく、手元ビルドの扱いの話。

v2 の UI を実際に使って確かめるには、手で操作してもらうか、ターミナルに画面収録とアクセシビリティの権限を与える必要がある。

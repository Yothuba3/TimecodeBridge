# LTC 耐障害性の検証 (2026-10-22)

v3.1.0 のタイムコード受信が、いろいろなフレームレートとノイズ条件でどこまで持つか、
信号が壊れたあと正常に戻ったときに正しく復帰するかを測った記録。

結論から書く。**実運用で想定される範囲では期待どおり動く。**
ノイズが信号と同じ大きさ(ノイズ比 1.0)まではフレームの取りこぼしなしで受信し、
それを超えると受信が落ちる。信号が戻れば、どれだけ強いノイズのあとでも、
また 30 秒途切れたあとでも、1 フレームの乱れもなく追従し、
復帰後のキューはきちんと 1 回だけ発火する。

ただし設計意図との食い違いが 1 件ある(後述の「ノイズ由来のフレームが通る」)。
実害は確認できなかったが、仕様どおりではない。

## 測り方

`tools/LtcResilience` を新しく作った。LTC エンコーダで本物の LTC 音声を作り、
白色雑音を混ぜてデコーダへ流し、連続性ゲートが何を採用したかを数える。
実機と同じ 48kHz・1024 サンプルのブロック単位で渡している。

ノイズ比は信号の振幅に対する雑音の振幅の倍率。1.0 で信号と同じ大きさ。
乱数の種は固定なので、同じ条件は何度でも同じ結果になる。

```
dotnet run --project tools/LtcResilience -- rates           # 全フレームレートでクリーン信号
dotnet run --project tools/LtcResilience -- sweep 30        # ノイズを上げて限界を探す
dotnet run --project tools/LtcResilience -- recover 3.0 3   # ノイズ → 無音 → 正常
dotnet run --project tools/LtcResilience -- dropout 30      # 信号が途切れて戻る
dotnet run --project tools/LtcResilience -- cues 1.2        # ノイズ下のキュー発火回数
dotnet run --project tools/LtcResilience -- e2e 1.5 --log   # 通しで 1 フレームずつ記録
```

判定の基準は `LtcContinuityGate` のクラスコメントに書かれた設計意図そのもの。
つまり「孤立ノイズは採用しない(未ロック時は 2 フレーム連続で初めてロック)」
「ロック中は 1 秒までの飛びを欠落とみなしてロックを保つ」
「それを超える前進や巻き戻しはロックを外して再ロックからやり直す」。

## フレームレートごとの素の受信

| レート | 期待 | 復号 | 採用 | 時刻のずれ |
|---|---|---|---|---|
| 24 | 120 | 119 | 119 | 0 |
| 25 | 125 | 124 | 124 | 0 |
| 29.97df | 150 | 149 | 149 | 0 |
| 30 | 150 | 149 | 149 | 0 |

4 種類すべてで取りこぼしなし。1 枚足りないのは末尾のフレームが
信号の終わりで切れているためで、異常ではない。

## どこまでノイズに耐えるか

4 つのレートすべてで同じ境界になった。

| ノイズ比 | 結果 |
|---|---|
| 0.5 まで | 全フレーム採用、時刻のずれ 0 |
| 1.0 | 全フレーム採用、時刻のずれ 0 |
| 1.1 | 採用率 86〜99%、わずかに乱れる |
| 1.2 | 採用がほぼ止まる(8〜11%、レートによっては 0) |
| 1.3 以上 | 受信不可 |

**時刻のずれなしで受信できる上限はノイズ比 1.00。**
信号と同じ振幅の雑音が乗っても平気で、そこから 10% 増えると劣化が始まり、
20% 増えると実質使えない。崖は急で、中間の「だらだら劣化する領域」はほとんどない。

## 正常信号に戻ったときの復帰

強いノイズを 3 秒 → 無音 3 秒 → きれいな信号 3 秒(時刻は 01 時台から 02 時台へ飛ばす)
という流れを、ノイズ比 1.2 / 1.5 / 2.0 / 3.0 で試した。4 条件すべて同じ結果。

- 無音中に採用したフレーム: **0**
- 復帰後に採用したフレーム: **89 / 90**
- 復帰後の最初の時刻: **02:00:00:00**(期待どおり)
- 復帰後の時刻のずれ: **0 フレーム**

ノイズ比 3.0、つまり信号の 3 倍の雑音を浴びせたあとでも、
復帰後の挙動はクリーン信号と区別がつかない。ノイズの影響を引きずらない。

## 信号が途切れて戻るとき

無音を 1 秒・5 秒・30 秒はさんだ。3 条件すべて、
戻ったあとの新しい時刻での乱れは **0 フレーム**、採用は 89/90。
30 秒飛んでも 2 フレーム連続で再ロックして追従する。

戻った直後に途切れる前の保留 1 枚(`01:00:02:29`)が先に出るが、
これはリングバッファに残っていた本物のフレームで、誤りではない。

## キューの発火

ノイズで時刻が乱れると、`CueManager` の巻き戻し検出が
発火済みの印を取り消して二重発火する恐れがある。実際に測った。

| ノイズ比 | ゲートが通した数 | キューの発火 |
|---|---|---|
| 0.0 | 149 | 1 回 |
| 1.0 | 149 | 1 回 |
| 1.1 | 148 | 1 回 |
| 1.2 | 12 | 0 回 |

**二重発火は一度も起きなかった。** ノイズ比 1.2 で 0 回なのは、
ゲートを通った 12 枚の中に発火時刻が含まれていない取りこぼしで、
誤発火とは逆の方向の失敗。本番の安全側に倒れている。

通しの試験(ノイズ → 無音 → 復帰後にキューを置く)も
ノイズ比 1.2 / 1.5 / 3.0 のすべてで **1 回だけ発火**した。
1 フレームずつの記録では、ノイズ由来の 4 枚のあと無音区間は空で、
復帰後 `01:00:10:15` でちょうど 1 回発火している。

```
  [ノイズ] 01:00:00:00
  [ノイズ] 01:00:00:04
  [ノイズ] 00:00:00:00
  [ノイズ] 00:00:00:03
  [正常 ] 01:00:10:00
  ...
  [正常 ] 01:00:10:15  ← 発火
```

## 想定と違ったこと: ノイズ由来のフレームが通る

ノイズ比 1.2 のとき、ゲートが採用した 12 枚のうち 6 枚が
`00:00:00:00` 付近の値だった。本物の信号は 01 時台なので、これは雑音が
偶然 LTC フレームとして解析されたもの。

```
01:00:00:00, 01:00:00:04, 00:00:00:00, 00:00:00:03, 00:00:00:00,
00:00:00:01, 00:00:01:00, 00:00:01:02, 01:00:02:01, 01:00:02:05, ...
```

ゲートのクラスコメントは「孤立ノイズを排除する」と書いている。
しかし未ロック時の再ロック規則は「直近フレームとの ordinal 差が 1〜7」であり、
ノイズ由来のフレームが 2 枚続いて偶然この条件に収まると通ってしまう。
雑音は 00 時台の小さい値に偏るので、2 枚が近い値になる確率は低くない。

実害は見つからなかった。二重発火は起きず、復帰も完全で、
そもそもこれが起きるのはノイズ比 1.2 という既に受信不可の領域だけ。
ただしコメントが約束していることと実装が一致していないので、記録しておく。

直すなら、未ロック時の再ロック条件に「2 枚の差がちょうど 1 ordinal」
という厳しい版を使う案がある。ただし 24fps の秒境界(フレーム 23 → 0)で
差が 7 になる事情があって `RelockDiff = 7` にしてあるので、
秒境界だけ例外にする必要がある。今回は手を入れていない。

## 途中で見つけた別の不具合

この検証のためにテストを足したとき、`tests/TimecodeBridge.App.Tests` が
そもそもコンパイルできないことに気づいた。`ICueManager` に
`AutoMuteOnManualTrigger` を足した d50f828 がこのテストプロジェクトの
スタブ 4 つを更新していなかった。コンパイルが通るようにしたうえで、
手動発火を発火手段として使っていたオートミュートのテスト 8 件を、
新しい既定値(手動ではミュートしない)に合わせて直した。
これで 257 件すべて通る。

macOS では v1 の WPF プロジェクトがビルドできないため
`dotnet test` を引数なしで回すと止まり、このテストプロジェクトまで
到達していなかったのが見逃した原因。
